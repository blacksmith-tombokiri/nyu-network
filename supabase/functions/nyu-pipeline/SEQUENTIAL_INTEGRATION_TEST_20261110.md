# ぜんにゅー API接続前の一気通貫パイプライン Ver.0.2

実装：2026年11月10日。接続するのは **ニュース取得 → 一次フィルター → 公式情報に基づくファクトパック確認・例外ルーティング → 安全装置付き模擬AI評価**。OpenAIへの有料アクセスおよび記事公開は実装・稼働ともに無効。

## 6時間ごとの運転時刻

Supabase pg_cron（UTC）で以下の4工程を順次起動。日本時間（JST）は9時間加算。

| JST | ステージ | Cron（UTC） | 上限 |
| --- | --- | --- | --- |
| 0:00 / 6:00 / 12:00 / 18:00 | fetch | 0 3,9,15,21 * * * | 許可済みRSSの配信元9件 |
| 0:05 / 6:05 / 12:05 / 18:05 | prefilter | 5 3,9,15,21 * * * | 新規最大500件 |
| 0:10 / 6:10 / 12:10 / 18:10 | route | 10 3,9,15,21 * * * | 10件×最大3回＝30件 |
| 0:15 / 6:15 / 12:15 / 18:15 | mock | 15 3,9,15,21 * * * | 2件までの模擬評価（適格な入力のみ） |

以前の「nyu-factpack-exception-routing」（毎日4回の単独ルーティング）は登録解除済み。新Cronは4工程の共通サイクルキーを参照する。**前工程が正常終了していなければ次工程はスキップ**。各工程は同一サイクルで1度しか開始できない。既存の `nyu_private.nyu_pipeline_runs` と別に `nyu_private.nyu_pipeline_cycles` で各ステージの状態と結果を記録する。

## アクセス制御と情報源

- `nyu-fetch-rss` v5 と `nyu-prefilter` v3 は、`is_active`、`rights_tier=green`、`production_enabled`、`commercial_use_allowed`、`reuse_status=approved`、takedownなしの条件を必須に変更
- RSSは加えて `auto_fetch_allowed`、有効なエンドポイントのみを取得
- 現在該当するRSS配信元は9件。HTML取得先は本番許可のない情報源が中心のため、このスケジュールには含めていない
- `nyu-prefilter` は新規記事だけをチェックし、完全に除外した記事は編集デスクに表示しない
- `nyu-factpack-auto` v13 は `ai_candidate` を優先処理し、`manual_review` も一部の制度・サービス変更候補に限り編集デスクへ登録する。それ以外の定型案内は二次除外記録に残す
- 自動確認に通過したファクトパックのJSONB配列／オブジェクト保存処理を修正。出典の曖昧さや今後の成果予測は自動確認に使わない

## 安全装置と限界

- Edge Function `nyu-pipeline` v2 で段階順序をチェック。非公開Vault `nyu_fetch_token` が必須
- `publish=true`、`provider=openai` などは拒否
- 最終工程は `nyu-ai-safety-runner` の `approved` に限り、実際に検証済みのファクトパックがなければ `no_approved_factpacks` で停止（模擬評価を捏造しない）
- 評価のスコアは **モック**。記事のDBへの新規掲載は行わない
- RSS取得の全部失敗でサイクルを失敗終了し、後続を実行しない。一部の配信元だけ失敗して他が成功した場合は取得結果に失敗件数を記録し、後続は進める
- 取得失敗後の再試行や5分を超える工程遅延に対する自動復旧は未実装。前工程が終了していなければ後続はスキップしてフェイルクローズ
- 取得・一次処理が最大件数に達した場合、取りこぼした未処理案件は次回サイクルの候補になる
- `manual_review` を自動承認してAI評価に渡すことはない

## 実テスト

テスト対象：デジタル庁のRSS。手動サイクル `manual_integration_digital_20261110`。

1. 実RSS取得：出典エンドポイントの正常取得と更新時刻を確認
2. 初回の完了記録で `cycle_stage_changed` が発生。原因はPL/pgSQLの動的SQL `EXECUTE` 後の `FOUND` 判定。修正して `GET DIAGNOSTICS ... = ROW_COUNT` を採用し、取得元の成功時刻を確認したうえでこのテストのfetch_done記録を手動復旧
3. 一次フィルター：10件（AI候補3、手動判断3、除外4）
4. ファクトパック確認・ルーティング：5件処理、要確認0、二次除外5、自動確認済み0
5. 模擬AI評価：認証済みのファクトパックがないため、`no_approved_factpacks` で安全にスキップ
6. すべての工程が `completed` まで到達。公開記事29件、評価記録130件は増えていない
7. 模擬ファクトパック判定12項目、模擬評価承認ゲート7項目が合格
8. 順番飛ばし・同じ工程の再実行は拒否（200＋`skipped:true`）。有料AIまたは記事公開の指示は409で拒否
9. `manual_review` の専用振り分けを対象10件でも実行（全件除外）。有料API呼び出し0、公開0
10. Cron4件の登録・有効化、旧単独Cronが存在しないことを確認

**未検証**：Cronによる次回の自動実行結果（手動サイクルでの結合試験とは別）、複数RSS全9件を同時に通す本番相当の運転、高負荷時のタイムアウト・再試行処理、管理画面ブラウザーでの動作、実記事の自動承認→模擬評価（現時点の実自動承認0件）。

## 重要な運用判断

現在はAI接続前の安全運転。API接続を許可する前に、失敗サイクルの再試行・タイムアウト監視、実際の承認済みファクトパックでの結合試験、入力スキーマとコスト上限の最終確認を行う。
